= 한국어 처리와 실무 구성

== 한국어 RAG의 품질을 좌우하는 구성요소

앞 장의 파이프라인을 한국어 문서에 적용하면 영어에서는 드러나지 않던 문제들이 나타난다. 조사와 어미가 붙어 형태가 바뀌는 단어, 분석기 사전에 없는 사내 용어, 마침표 없이 길게 이어지는 문장 같은 것들이다. 품질을 좌우하는 구성요소를 하나씩 확인한다.

=== 임베딩 모델의 한국어 이해

벡터 검색의 품질은 임베딩 모델이 한국어 문장의 의미를 벡터에 얼마나 잘 담는지에 달렸다. 예를 들어 "연차"와 "휴가"처럼 뜻이 가까운 표현이 가까운 벡터로 나와야 한다. OpenAI `text-embedding-3`, Cohere, Voyage, BGE-M3 같은 다국어 모델의 한국어 품질이 좋아지고 있다. 도메인에 따라서는 KURE 같은 한국어 특화 모델이 유리할 수 있다.

선택할 때는 MTEB 한국어 벤치마크를 참고하되, 최종 선택은 자기 도메인 문서로 직접 평가해서 정한다. 벤치마크는 일반 텍스트 기준이라, 사내 용어와 문서 형식이 특수한 도메인에서는 순위가 뒤집히는 일이 흔하다.

한 가지 구분해 둘 것이 있다. 벡터 검색 경로의 토큰화는 임베딩 모델 내부의 토크나이저가 처리하므로, 모델을 바꾸는 것 말고는 개발자가 손댈 부분이 거의 없다. 개발자가 직접 다뤄야 하는 토큰화는 키워드 검색 경로에 있다.

=== 형태소 분석과 사용자 사전

형태소 분석은 한국어 키워드 검색에서 가장 까다로운 부분이다. 앞 장에서 본 것처럼 조사와 어미 때문에 공백 토큰화가 통하지 않는다. 그래서 Elasticsearch/OpenSearch의 Nori 분석기나 Mecab-ko, Khaiii, KIWI 같은 형태소 분석기로 조사와 어미를 떼어 낸 단어를 뽑아야 한다. 예를 들어 "은행에서"에서는 "은행"을, "접속했다"에서는 "접속"을 얻는다.

형태소 분석기를 도입했다고 끝나지 않는다. 신조어, 사내 용어, 제품명은 분석기의 기본 사전에 없어서 엉뚱하게 쪼개진다. 예를 들어 사내 시스템 이름이 일반 명사 두 개로 분해되면 그 이름으로는 검색이 안 된다. 이런 단어는 사용자 사전(custom dictionary)에 등록해서 한 단어로 분석되게 한다. 사전을 얼마나 잘 관리하느냐가 검색 품질로 바로 이어지고, 문서와 용어가 늘어나는 한 이 작업은 계속된다.

=== 청킹 전략

한국어 문장은 연결 어미("~하고", "~하며")로 여러 절이 이어져 길어지는 경우가 많아, 고정 길이로 자르면 의미 단위가 중간에 끊기기 쉽다. 개선 방향은 세 단계다.

1. *문장 분리 정비*: "다.", "요."뿐 아니라 "함.", "임." 같은 명사형 종결, 마침표 없는 줄바꿈, 표와 리스트 마크업까지 문장 경계로 처리한다.
2. *의미 단위 청킹*: 인접한 두 문장의 임베딩 유사도가 급격히 떨어지는 곳에서 자른다. 주제가 바뀌는 위치를 자동으로 찾는 방식이라, 한국어처럼 형식적 단서(마침표, 제목, 문단 구분)가 부족한 텍스트에 효과적이다.
3. *계층적 청킹*: 검색은 문단 크기의 작은 청크로 해서 정확도를 높이고, LLM에는 그 청크가 속한 절처럼 더 큰 단위를 전달해 문맥을 확보한다.

=== 재순위 모델

검색 상위 후보들을 cross-encoder 모델로 다시 정밀 채점하는 단계다. 임베딩 검색은 질의와 문서를 각각 따로 벡터로 만들어 비교하지만, cross-encoder는 질의와 문서를 한 쌍으로 함께 읽고 관련도를 판정하므로 더 정확하다. 대신 문서 벡터처럼 미리 계산해 둘 수 없고, 질의가 들어올 때마다 후보 문서를 하나씩 질의와 함께 모델에 넣어야 해서 느리다. 그래서 전체 문서가 아닌 상위 후보 수십 개에만 적용한다.

Cohere Rerank 다국어판, BGE-reranker, Jina reranker가 자주 쓰인다. 한국어 전용 reranker는 선택지가 적어서 다국어 모델로 시작하고, 필요하면 자체 데이터로 파인튜닝을 검토한다.

=== 쿼리 처리

한국어 질문은 구어체, 줄임말, 오타가 많다. 사용자의 입력을 그대로 검색하는 대신 전처리하는 방법이 두 가지 있다. 쿼리 재작성은 LLM이 질문을 검색하기 좋은 문장으로 고쳐 쓰게 하는 방법이다. 예를 들어 "연차 남은 거 내년에 씀?"을 "사용하지 않은 연차의 다음 해 이월 규정"으로 바꾼다. HyDE(Hypothetical Document Embeddings)는 질문에 대한 가상의 답변 문서를 LLM으로 생성한 뒤 그 문서로 검색하는 기법이다. 질문("연차가 이월되나요?")과 문서("사용하지 않은 연차는 다음 해 3월까지 이월된다.")는 문체가 달라 벡터 공간에서 멀 수 있다. 가상 답변은 문서처럼 평서문으로 쓰이므로 실제 답변 문서와 더 가깝게 검색된다.

== Spring AI로 옮긴 파이프라인

이제 앞 장의 최소 구현을 Spring AI로 옮긴다. 이 절의 목표는 앞 절에서 꼽은 구성요소를 모두 갖춘 시스템을 만드는 것이 아니다. Spring AI는 RAG 파이프라인의 각 단계를 컴포넌트로 제공하므로, 각 단계가 어느 컴포넌트에 대응하는지 확인하는 것이 목표다. 예제 프로젝트(`examples/spring-ai`)는 ONNX로 변환된 임베딩 모델(all-MiniLM-L6-v2)을 자바 프로세스 안에서 로컬 실행하므로 API 키가 필요 없다. 9장에서 본 것처럼 ONNX로 변환된 모델을 ONNX Runtime이 실행하기 때문에 가능한 구성이다. 대신 이 임베딩 모델은 영어 중심이고, 하이브리드 검색과 형태소 분석, 재순위는 예제에 없다. 앞 절의 구성요소들은 이 파이프라인에 하나씩 더할 수 있다. 어느 것을 먼저 더할지는 다음 장의 진단 순서에 따라 정한다.

== RAG 안에서 쓰이는 LLM들

여기까지 보면 RAG 시스템 하나에 모델이 여러 개 들어간다는 것을 알 수 있다. 위치마다 모델에 필요한 특성이 다르다.

[cols="1,2,2"]
|===
| 위치 | 역할 | 필요한 특성

| 임베딩 모델
| 텍스트를 벡터로 변환
| 한국어 품질, 적절한 차원 수, 속도, 긴 입력 지원

| 쿼리 재작성/분기
| 질문 정제, 인덱스 선택
| 작고 빠른 instruction-following 모델로 충분

| 재순위 모델
| 후보 K개를 정밀 채점
| cross-encoder 전용 모델이 효율적

| 응답 생성 LLM
| 검색 컨텍스트 기반 최종 답변
| 긴 컨텍스트, 인용 능력, 환각 억제, 한국어 자연스러움

| 평가/가드레일
| 응답의 충실성과 안전성 검증
| 작은 모델의 LLM-as-a-judge로 가능
|===

설계 원칙은 "쿼리 처리는 작고 빠른 모델, 최종 생성은 큰 모델"이다. 질의 시점 파이프라인에서 여러 번 호출되는 앞 단계들은 지연과 비용이 누적되므로 작은 모델을 쓰고, 사용자가 읽을 최종 답변에만 큰 모델을 쓴다.

주의할 특성이 하나 있다. 검색 결과를 잘 활용하는 능력(groundedness, 컨텍스트 충실도)은 모델마다 다르다. 일반 벤치마크 점수가 높은 모델이 "주어진 문맥에만 근거해 답하기"도 잘한다는 보장이 없으므로, 이 능력은 별도로 측정해야 한다. 측정 방법을 포함한 성능 진단 전체를 다음 장에서 다룬다.
