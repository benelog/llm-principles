[[ch-rag-tuning]]
= 성능 진단과 개선 우선순위

== 증상이 아니라 단계로 말하기

RAG 시스템의 흔한 상황은 이렇다. 데모는 그럴듯했는데 실사용 질문에는 엉뚱한 답이 나온다. "답변이 이상하다"는 증상만으로는 아무것도 고칠 수 없다. 파이프라인의 어느 단계가 실패했는지를 찾아야 하고, 실패는 네 단계로 나뉜다. 순서대로 진단한다.

== 1단계: 검색 실패

가장 흔한 원인이다. 정답이 담긴 청크를 검색이 처음부터 못 찾는 경우다.

진단 방법은 단순하다. 실패한 질문에 대해 검색 결과 top-K(예: 20개)를 직접 눈으로 확인한다. 정답이 담긴 청크가 그 안에 없다면 검색 실패다. 이 상태에서 생성 모델을 아무리 바꿔도 소용없다. 모델은 입력된 토큰에만 답할 수 있기 때문이다.

해결 수단은 다음과 같다.

* 한국어 품질이 더 좋은 임베딩 모델로 교체한다.
* 벡터 + BM25 하이브리드 검색을 도입한다. 10장에서 본 것처럼 고유명사와 코드성 질의는 키워드 검색이 잡아 준다.
* 청킹을 재설계한다. 한국어는 300~800 토큰에서 시작해서 조정한다. 청크가 너무 크면 벡터가 뭉개지고, 너무 작으면 문맥이 끊긴다.
* 메타데이터 필터로 검색 공간을 좁힌다. 전체 문서가 아니라 해당 제품, 해당 기간의 문서에서만 찾게 한다.
* 키워드 검색 경로의 토큰화를 점검한다. 11장의 형태소 분석기와 사용자 사전 문제다.

== 2단계: 순위 실패

top-20에는 정답이 있는데 top-3에는 없는 상태다. 검색기가 정답을 찾긴 했지만 LLM에 전달되는 상위권에 올리지 못했다. 컨텍스트에 넣을 수 있는 청크 수는 토큰 예산 때문에 제한되므로, 상위 몇 개 안에 들어야 실제로 전달된다.

* reranker를 추가한다. 이 단계의 해결책 중 비용 대비 효과가 가장 크다. 상위 후보만 cross-encoder로 다시 채점하므로 지연 증가도 감당할 만하다.
* 쿼리 재작성으로 모호한 질문을 정제한다.
* 질문을 여러 변형으로 바꿔 각각 검색한 뒤 합치는 multi-query를 쓴다.

== 3단계: 생성 실패

검색은 잘 됐는데 최종 응답이 틀리거나 환각이 섞이는 상태다. 정답이 컨텍스트에 있는데도 모델이 그것을 쓰지 않거나 왜곡한다.

* 프롬프트 구조를 정비한다. "주어진 문맥에만 근거해 답하라", "문맥에 없으면 모른다고 답하라"를 명시한다.
* 중요 문서를 컨텍스트의 맨 앞이나 맨 뒤에 배치한다. 2장에서 본 "lost in the middle", 즉 모델이 긴 컨텍스트의 중간 내용을 놓치는 현상을 피하기 위해서다.
* citation을 강제한다. 답변의 각 주장에 출처 청크 번호를 붙이게 하면 환각이 줄고, 사용자가 검증할 수도 있다.
* 생성 모델을 업그레이드한다. 단, 1~2단계가 정상일 때만 효과가 있다.

== 4단계: 평가 부재

앞의 세 단계를 진단하려면 "정답이 담긴 청크"와 "맞는 답변"이 무엇인지 정의되어 있어야 한다. 평가셋이 없으면 어떤 변경이 개선인지 판단할 수 없고, 튜닝은 인상 비평이 된다. 근본적인 문제라서 마지막 단계로 두었지만, 실제로는 가장 먼저 해결해야 한다.

* 질문-정답-출처 3요소로 평가 데이터셋을 만든다. 50~100개로 시작해도 된다. 실사용 로그에서 실패한 질문을 모으는 것이 좋은 출발이다.
* 단계별 지표를 둔다. 검색은 recall@K(정답 청크가 top-K에 드는 비율)와 MRR(정답의 평균 순위), 생성은 faithfulness(컨텍스트 충실도)와 answer relevance(질문 적합도).
* Ragas, TruLens 같은 평가 프레임워크를 활용하고, LLM-as-a-judge로 자동화하되 주기적으로 사람 평가와 대조해서 채점 기준이 어긋나지 않았는지 확인한다.

단계별 지표가 있어야 변경의 효과를 단계별로 귀속시킬 수 있다. 임베딩 모델을 바꿨는데 최종 답변 품질만 보고 있다면, 검색이 좋아졌는데 생성이 그것을 못 살리는 상황과 검색부터 나빠진 상황을 구분할 수 없다.

== 개선 우선순위

지금까지의 내용을 실행 순서로 정리하면 다음과 같다.

1. *평가셋부터 만든다.* 없으면 나머지 작업의 효과를 측정할 수 없다.
2. *하이브리드 검색을 기본으로 한다.* 벡터 검색만으로는 부족하다.
3. *한국어라면 형태소 분석기와 사용자 사전을 정비한다.* 키워드 검색 경로의 비중이 크다.
4. *reranker를 도입한다.* 비용 대비 효과가 크다.
5. *생성 모델 업그레이드는 마지막에 한다.* 가장 비싸고, 앞 단계가 부실하면 효과가 적다.

목록의 위쪽일수록 저렴하고 효과가 확실하며, 아래쪽일수록 비싸고 앞 단계에 의존한다. 흔한 실수는 이 순서를 거꾸로 밟는 것이다. 답변이 이상하니 더 큰 생성 모델을 쓰고, 그래도 이상하니 프롬프트를 고치는 식인데, 정작 문제는 검색이 정답을 가져오지 못하는 데 있는 경우가 대부분이다.

이 순서를 관통하는 결론은 하나다. RAG의 성능 개선은 더 큰 모델이 아니라 더 정확한 검색에서 온다. 2부에서 본 것처럼 모델은 입력된 토큰의 통계적 연장을 생성할 뿐이므로, 좋은 답의 재료는 검색이 가져다 놓아야 한다. 1부의 분류로 돌아가면, 컨텍스트 공급 레이어의 품질이 프롬프트 레이어와 모델 레이어가 할 수 있는 일의 상한을 정한다.

다음 장에서는 이 뼈대를 흔드는 두 가지 변화를 다룬다. 수백만 토큰으로 커진 컨텍스트 윈도우와, 검색을 파이프라인이 아니라 도구로 다루는 에이전트의 등장이다.
