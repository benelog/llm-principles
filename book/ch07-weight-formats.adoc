= 가중치 저장 포맷

== 모델 파일의 정체

2부에서 학습시킨 microGPT의 실체는 4,192개의 실수값이었다. 프로덕션 모델도 마찬가지로, 학습이 끝난 모델의 실체는 텐서(다차원 배열)들의 모음이다. 토큰 임베딩 행렬, 각 블록의 어텐션 가중치, MLP 가중치가 이름이 붙은 텐서로 존재한다. 모델 파일이란 이 텐서들을 이름과 함께 담은 바이너리다.

Hugging Face에서 모델을 받으면 `model.safetensors` 같은 파일이 수 GB를 차지한다. 이 파일을 어떤 형식으로 저장하느냐가 오픈 모델 호환성의 첫 번째 표준이다. 현재 쓰이는 포맷은 세 계열이다.

[cols="1,3"]
|===
| 포맷 | 특징

| Safetensors
| 현재의 표준. 헤더가 JSON이라 어느 언어에서든 해석할 수 있고, 메모리 매핑을 지원하며, 코드 실행 없이 데이터만 읽으므로 안전하다.

| GGUF
| llama.cpp 생태계의 표준. 양자화 정보를 포함하고 CPU와 엣지 환경에 강하다. Ollama가 이 포맷을 쓴다.

| PyTorch (.bin/.pt)
| 레거시 포맷. 파이썬 pickle 기반이라 파일을 여는 것만으로 임의 코드가 실행될 수 있는 보안 취약점이 있다.
|===

== pickle의 문제와 Safetensors의 등장

레거시 포맷의 문제를 짚고 넘어갈 필요가 있다. PyTorch의 기본 저장 방식은 파이썬 pickle 직렬화 위에 만들어져 있다. pickle은 파이썬 객체를 저장하면서 "이 객체를 복원하는 방법"까지 담는데, 그 복원 방법에 임의의 함수 호출이 들어갈 수 있다. 악의적으로 만든 모델 파일을 ``torch.load``로 여는 순간 학습된 숫자 대신 공격 코드가 실행될 수 있다는 뜻이다.

모델을 "누구나 올리고 누구나 받는" 허브가 성장하면서 이 위험은 실제 공격 경로가 되었다. Safetensors는 이 문제를 구조적으로 제거한 포맷이다. 파일에는 순수한 데이터와 JSON 메타데이터만 있고, 실행 가능한 것이 아무것도 없다. 여기에 두 가지 실용적 장점이 더해졌다. 헤더만 읽으면 전체 데이터를 메모리에 올리지 않고도 모델 구조를 알 수 있고, 메모리 매핑으로 필요한 부분만 지연 로딩할 수 있다.

GGUF는 다른 방향의 요구에서 나왔다. GPU 없이 CPU에서 모델을 돌리려면 가중치를 4비트, 5비트로 압축하는 양자화가 필수인데, GGUF는 양자화 방식과 실행에 필요한 메타데이터를 파일 하나에 담아 llama.cpp 계열 엔진이 바로 실행할 수 있게 한다.

== safetensors를 직접 만들어 보기

포맷이 얼마나 단순한지는 직접 만들어 보면 안다. safetensors 파일의 구조는 세 부분이다. 처음 8바이트에 헤더 길이, 이어서 JSON 헤더, 그 뒤에 텐서 데이터가 이어진다. 이 절의 코드는 ``examples/go/safetensors``에 있으며 표준 라이브러리만으로 동작한다.

헤더에 기록되는 텐서 하나의 메타데이터를 Go 타입으로 표현하면 다음과 같다.

[source,go]
----
include::../examples/go/safetensors/main.go[tag=header-type,indent=0]
----

파일을 쓰는 쪽은 텐서들을 바이트로 이어 붙이면서 각 텐서의 위치를 헤더에 기록한다.

[source,go]
----
include::../examples/go/safetensors/main.go[tag=write,indent=0]
----

읽는 쪽은 그 반대다. 헤더 길이를 읽고, JSON을 해석하고, 오프셋으로 텐서를 찾아간다.

[source,go]
----
include::../examples/go/safetensors/main.go[tag=read,indent=0]
----

실행하면 어휘 4개, 임베딩 차원 3인 장난감 모델이 저장되고 복원된다. 실제 LLM의 safetensors 파일도 텐서가 수백 개이고 원소가 수십억 개일 뿐 구조는 같다. 파서 어디에도 코드 실행이 없다는 것, JSON과 바이트 오프셋만 다루면 어떤 언어로도 읽고 쓸 수 있다는 것이 이 포맷이 표준이 된 이유를 그대로 보여 준다.

== 샤딩: 여러 파일로 나뉜 모델

실제 모델 저장소에서는 가중치가 파일 하나가 아니라 ``model-00001-of-00004.safetensors``처럼 여러 조각으로 나뉘어 있는 경우가 많다. 함께 있는 ``model.safetensors.index.json``이 어느 텐서가 어느 조각에 들었는지를 기록한 색인이다. 파일을 나누는 이유는 실용적인 것들이다. 조각 단위로 병렬 다운로드와 재시도가 가능하고, 저장소나 파일 시스템의 파일 크기 제한을 피할 수 있으며, 여러 GPU에 모델을 나눠 올릴 때 필요한 조각만 읽을 수 있다. 구조는 앞 절에서 만든 파일이 여러 개로 늘고 색인 JSON이 하나 얹힌 것뿐이다.

== 양자화: 정밀도를 낮춰 크기를 줄이기

가중치 파일의 크기는 "파라미터 수 × 파라미터 하나의 바이트 수"로 정해진다. 파라미터 하나를 몇 바이트로 저장할지가 데이터 타입이고, 정밀도를 낮춰 바이트 수를 줄이는 것이 양자화(quantization)다.

[cols="1,1,3"]
|===
| 타입 | 크기 | 용도

| FP32
| 4바이트
| 전통적인 학습 기본값. 유통용으로는 과잉이라 점점 드물다

| FP16 / BF16
| 2바이트
| 현재 유통되는 모델의 표준. BF16은 표현 범위가 FP32와 같아 학습 안정성에서 유리하다

| INT8
| 1바이트
| 추론용 양자화. 품질 저하가 대체로 작다

| 4비트(INT4, NF4 등)
| 0.5바이트
| 메모리가 부족한 환경의 추론용. 품질 저하가 나타나기 시작한다
|===

이 표만으로 필요한 메모리를 어림할 수 있다. 파라미터 70억 개(7B) 모델은 BF16으로 약 14GB, 4비트 양자화로 약 4GB다(블록별 보정 정보가 조금 더 붙는다). "이 모델이 내 GPU에 올라가는가"라는 질문의 답이 곱셈 한 번으로 나온다.

GGUF 파일 이름에 붙는 `Q4_K_M` 같은 접미사가 양자화 방식의 표기다. 숫자는 비트 수를, 나머지는 블록 단위 보정 방식을 나타낸다. 양자화는 값을 단순히 반올림하는 것이 아니라 가중치를 블록으로 묶고 블록마다 배율을 따로 저장하는 식으로 오차를 줄이는데, 같은 4비트라도 방식에 따라 품질이 달라서 GGUF 생태계에서는 크기와 품질의 절충안이 접미사가 다른 파일들로 함께 배포된다.

양자화는 3장에서 본 QLoRA의 절반이기도 하다. 원본 가중치를 4비트로 줄여 메모리를 아끼고 그 위에 LoRA 어댑터만 학습하는 조합이었다. 저장 포맷의 문제로 보였던 양자화가 학습 기법과 연결된다.

== 양자화 알고리즘의 원리

앞 절에서 양자화가 "가중치를 블록으로 묶고 블록마다 배율을 저장한다"고 했다. 이 절에서는 그 말의 실체를 코드로 확인한다. 예제는 ``examples/go/quantize``에 있으며 표준 라이브러리만으로 동작하고, 무작위 시드를 고정했으므로 출력이 그대로 재현된다.

=== 선형 양자화: 비례식 하나

가장 단순한 양자화는 실수 구간을 정수 격자에 비례식으로 대응시키는 것이다. INT8이라면 가중치의 최대 절댓값이 127에 오도록 배율(scale)을 정하고, 모든 값을 그 배율로 나눠 반올림한다.

[source,go]
----
include::../examples/go/quantize/main.go[tag=absmax,indent=0]
----

고등학교에서 배운 일차함수 그대로다. 잃는 것은 반올림에서 생기는 오차뿐이고, 오차의 최대치는 격자 간격의 절반이다. 표준편차 1.0인 정규 분포에서 뽑은 가중치 4,096개로 측정한 결과다.

----
== 선형 양자화 (표준편차 1.0인 가중치 4,096개) ==
INT8 (격자 255개):  RMS 오차 0.0084
4비트 (격자 15개):  RMS 오차 0.1525
----

격자가 촘촘한 INT8에서는 오차가 값 크기의 1% 아래지만, 격자가 15개뿐인 4비트에서는 뚜렷하게 커진다. 앞 절의 표에서 "4비트부터 품질 저하가 나타나기 시작한다"고 했던 것이 이 숫자다.

=== 아웃라이어와 블록 단위 배율

문제는 배율이 최대 절댓값 하나로 정해진다는 데 있다. 트랜스포머의 가중치와 활성값에는 다른 값보다 수십 배 큰 아웃라이어가 종종 나타나는데, 그 값 하나가 배율을 끌어올리면 나머지 모든 값이 성긴 격자로 밀려나 오차가 커진다. 해법은 배열을 블록으로 잘라 블록마다 배율을 따로 두는 것이다.

[source,go]
----
include::../examples/go/quantize/main.go[tag=blocks,indent=0]
----

----
== 아웃라이어 하나가 끼면 (w[0]을 20.0으로) ==
4비트, 텐서 전체에 배율 하나:  RMS 오차 0.7786
4비트, 64개 블록마다 배율:     RMS 오차 0.1385
----

4,096개 중 값 하나를 20.0으로 바꿨을 뿐인데 전체 오차가 다섯 배로 뛰고, 블록마다 배율을 두면 피해가 아웃라이어가 든 블록 하나로 국한되어 원래 수준으로 돌아온다. 이것이 블록 단위 보정의 실체이고, GGUF의 `Q4_K_M` 같은 방식들은 블록 크기와 배율 저장 방법(배율 자체를 다시 양자화하는 것까지)을 서로 다르게 조합한 변형들이다.

=== 격자를 어디에 둘 것인가: NF4와 정규 분포

균등 간격 격자가 최선인 것도 아니다. 학습된 가중치는 대체로 평균 0 주변에 몰려 있고 큰 값일수록 드문, 정규 분포에 가까운 모양이다. 값이 0 근처에 밀집해 있는데 격자를 같은 간격으로 깔면 값이 거의 없는 꼬리 쪽 격자점이 낭비된다. QLoRA가 쓰는 NF4(NormalFloat 4비트)는 격자점을 정규 분포의 분위수에, 즉 격자점마다 담당하는 값의 개수가 비슷해지도록 배치해서 같은 16개 점으로 더 작은 오차를 얻는다.

[source,go]
----
include::../examples/go/quantize/main.go[tag=normal-grid,indent=0]
----

----
== 격자를 어디에 둘 것인가 (아웃라이어 없는 원본, 격자 16개) ==
균등 간격 격자:         RMS 오차 0.1447
정규 분포 분위수 격자:  RMS 오차 0.1070
----

같은 4비트인데 격자 배치만 바꿔 오차가 4분의 1 넘게 줄었다. 값이 어디에 몰리는지 알면 정밀도를 그쪽에 몰아 줄 수 있다는 원리이며, 정규 분포가 왜 이런 곳에서 나타나는지는 부록 수학·통계 기초의 정규 분포 절에서 다룬다.

=== 보정 데이터를 쓰는 방식: GPTQ와 AWQ

지금까지의 방식은 가중치 값만 보고 반올림했다. 한 걸음 더 나간 방식들은 "가중치 값의 오차"가 아니라 "그 가중치가 만드는 레이어 출력의 오차"를 줄인다. 대표 텍스트 몇백 건(보정 데이터)을 모델에 흘려 보면서 반올림을 조정하는 것이다.

GPTQ는 가중치를 하나씩 양자화하면서, 방금 반올림으로 생긴 출력 오차를 아직 양자화하지 않은 가중치들을 미세하게 움직여 보상한다. AWQ는 보정 데이터에서 활성값이 큰 채널, 즉 출력에 크게 기여하는 소수의 가중치를 찾아 그쪽의 오차가 작아지도록 채널별 배율을 조정한다. 두 방식의 출발점은 같은 관찰이다. 모든 가중치가 똑같이 중요하지는 않으므로, 중요한 쪽의 정밀도를 지키는 방향으로 오차를 배치할 수 있다.

허브에서 이름에 `-GPTQ`, ``-AWQ``가 붙은 모델 저장소가 이 방식으로 양자화된 가중치이고, 원 논문들은 부록 더 읽을거리에 정리해 두었다.

== 가중치 안에 무엇이 들어 있나

이 텐서들 안에 무엇이 들어 있는지 다시 확인해 두자. 다국어를 지원하는 모델도 언어별 파일이 따로 있지 않다. 한국어 문법도, 영어 어휘도, 코드 작성 능력도 전부 같은 텐서들의 숫자값에 "분산 표현"으로 녹아 있다. 1부에서 모델 레이어의 정보를 선택적으로 빼내기 어렵다고 한 이유가 이 저장 방식에 있다. 특정 지식을 담당하는 파일이나 영역이 없으므로, 파일을 들여다봐서 모델이 무엇을 아는지 알아낼 방법도 없다.

가중치 파일은 숫자를 담을 뿐, 그 숫자를 어떤 구조에 배치해서 실행할지는 알려 주지 않는다. 그 정보는 별도의 설정 파일에 있으며, 그것이 두 번째 표준이다. 다음 장에서 다룬다.
