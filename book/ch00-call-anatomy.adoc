= 도입: LLM 호출 한 번의 해부

이 장은 LLM을 처음 다루는 독자를 위한 출발점이다. LLM API 호출 한 번을 요청과 응답의 필드 단위로 해부하면서, 책 전체에서 쓸 기본 개념인 학습, 추론, 토큰, 컨텍스트 윈도우를 가장 구체적인 자리에서 정의한다. 그리고 이 한 번의 호출에서 생기는 질문들이 이 책의 어느 장으로 이어지는지 지도를 그린다. LLM API를 이미 호출해 본 독자라면 마지막 절의 지도만 훑고 1장으로 넘어가도 된다.

== 만드는 단계와 쓰는 단계

LLM(Large Language Model, 대규모 언어 모델)은 입력된 텍스트에 이어질 텍스트를 만들어 내는 프로그램이다. ChatGPT 같은 챗봇 서비스는 이 프로그램에 대화 화면을 씌운 것이고, 애플리케이션 개발자는 화면 대신 HTTP API로 같은 프로그램을 호출한다.

이 프로그램의 수명은 두 단계로 나뉜다.

학습(training)::
대량의 텍스트 데이터를 이용해 모델 내부의 숫자들(파라미터)을 조정하는 과정이다. 모델을 만드는 단계이며, GPU 클러스터에서 수개월씩 걸리는 작업부터 몇 시간짜리 작업까지 여러 층위가 있다. 1부에서 그 층위를 분류하고, 2부에서 작은 규모로 직접 실행해 본다.

추론(inference)::
학습이 끝난 모델에 입력을 넣고 출력을 받는 일이다. 챗봇에 질문을 입력하는 것도, 애플리케이션이 API를 호출하는 것도 추론 요청 하나다. 이 책에서 "추론 시점"은 이 호출이 처리되는 순간을 가리킨다. 모델이 논리적으로 생각을 전개한다는 뜻의 추론(reasoning)과는 다른 말이므로, 이 책에서 후자를 가리킬 때는 "추론 능력", "중간 추론"처럼 문맥을 붙여 쓴다.

애플리케이션 개발자의 일은 대부분 추론 쪽에 있다. 학습은 모델을 만든 조직이 이미 끝냈고, 개발자는 그 결과물을 호출한다. 그런데도 이 책이 학습을 계속 다루는 이유는, 추론에서 만나는 현상들(답변의 품질, 말투, 지식의 한계)의 원인이 학습에 있기 때문이다.

== 요청의 생김새

실제 호출 하나를 보자. 상용 API든 로컬에서 띄운 오픈 모델이든, 채팅형 LLM의 HTTP 요청은 대체로 다음 형태다. 필드 이름은 제공자마다 조금씩 다르지만, OpenAI 호환 형식이라고 불리는 이 구조가 널리 쓰인다.

[source,json]
----
{
  "model": "llama-3.1-8b-instruct",
  "messages": [
    {"role": "system", "content": "너는 사내 IT 헬프데스크 도우미다. 사내 규정에 근거해서 답한다."},
    {"role": "user", "content": "VPN 비밀번호를 잊어버렸는데 어떻게 재설정하나요?"}
  ],
  "temperature": 0.7
}
----

필드 세 개가 이 책의 큰 구획과 그대로 대응한다.

`model`::
어느 모델을 쓸지 지정한다. 이 이름의 실체는 학습으로 결정된 수십억 개의 숫자, 즉 파라미터 뭉치다. 같은 요청도 모델이 다르면 답이 달라지는 이유는 이 숫자들이 다르기 때문이다. 파라미터에 무엇이 어떻게 담기는지가 1장, 이 숫자들이 파일로 저장되어 유통되는 방식이 3부의 주제다.

`messages`::
모델에 전달할 대화다. role은 발화의 주체를 표시한다. system은 애플리케이션이 심는 지시, user는 사용자의 입력, assistant는 모델의 이전 답변이다. 모델이 이미 아는 것(파라미터)과 별개로, 이 배열에 담아 보내는 것이 추론 시점에 공급되는 정보의 전부다. 여기에 무엇을 어떻게 담을지가 1부의 주제이고, 이 배열이 모델이 실제로 받는 형태로 바뀌는 규칙은 9장에서 다룬다.

`temperature`::
출력의 다양성을 조절하는 값이다. 낮으면 매번 비슷한 답이, 높으면 요청마다 다른 답이 나온다. 같은 입력에서 어떻게 다른 출력이 나올 수 있는지는 다음 절에서 설명한다. 이런 생성 제어 파라미터들은 3장에서 정리하고, 5장에서 코드 수준으로 확인한다.

== 응답의 생김새

[source,json]
----
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "사내 포털의 '계정 관리 > 비밀번호 재설정' 메뉴에서 재설정할 수 있습니다. ..."
    },
    "finish_reason": "stop"
  }],
  "usage": {
    "prompt_tokens": 67,
    "completion_tokens": 52,
    "total_tokens": 119
  }
}
----

`message.content`가 모델이 생성한 답변이다. 그런데 개발자가 그냥 지나치기 쉬운 필드가 하나 있다. `usage`다. 입력이 67, 출력이 52라는 이 숫자들의 단위가 토큰이고, LLM을 다루는 내내 따라다니는 개념이다.

토큰(token)::
모델이 텍스트를 읽고 쓰는 단위다. 모델은 문자나 단어가 아니라 토큰이라는 조각 단위로 텍스트를 다룬다. 한 토큰은 영어에서는 대체로 단어 하나이거나 그 일부이고, 한국어는 그보다 잘게 쪼개지는 경우가 많다(왜 그런지는 9장에서 다룬다). 상용 API의 과금은 이 usage의 토큰 수 기준이며, 입력과 출력의 단가가 다르다(그 이유는 6장에서 밝혀진다).

응답에 대해 알아 둘 사실이 두 가지 더 있다.

첫째, 모델은 답변을 통째로 만들지 않는다. 토큰을 하나 만들고, 그것까지 포함한 입력으로 다음 토큰을 만드는 일을 답이 끝날 때까지 반복한다. 챗봇 화면에서 답이 한 글자씩 흘러나오는 스트리밍은 연출이 아니라 이 생성 방식이 그대로 보이는 것이다. temperature가 조절하는 것도 이 반복의 매 단계에서 다음 토큰을 확률적으로 뽑는 방식이다. 이 "다음 토큰 예측"이 2부 전체의 주제다.

둘째, 방금 답변의 내용이 맞는지는 아무도 보장하지 않는다. 모델은 학습 때 흡수한 통계로 그럴듯한 텍스트를 만들 뿐이므로, 사내 규정처럼 학습 데이터에 없던 사실은 지어낼 수 있다. 시스템 프롬프트에 "사내 규정에 근거해서 답한다"라고 썼다고 해서 모델에 사내 규정이 생기지는 않는다. 규정 문서를 찾아서 messages에 함께 넣어 주는 시스템이 따로 필요하고, 그것이 4부에서 다루는 RAG다.

== 호출 사이에는 아무것도 남지 않는다

처음 다루는 사람을 자주 놀라게 하는 사실이 하나 있다. 모델은 요청 사이에 아무것도 기억하지 않는다. 방금의 VPN 질문에 이어 사용자가 "그 메뉴가 안 보이는데요?"라고 물으면, 애플리케이션은 이전 질문과 답변까지 포함한 배열 전체를 다시 보내야 한다.

[source,json]
----
{
  "messages": [
    {"role": "system", "content": "너는 사내 IT 헬프데스크 도우미다. ..."},
    {"role": "user", "content": "VPN 비밀번호를 잊어버렸는데 어떻게 재설정하나요?"},
    {"role": "assistant", "content": "사내 포털의 '계정 관리 > ..."},
    {"role": "user", "content": "그 메뉴가 안 보이는데요?"}
  ]
}
----

챗봇 화면이 보여 주는 "대화"는 서비스가 밖에서 쌓아 관리하는 것이고, 모델 입장에서는 매번 처음 보는 요청 하나일 뿐이다. 여기서 두 가지가 따라 나온다. 대화가 길어질수록 매 턴에 다시 보내는 토큰이 늘어나 비용이 누적된다는 것, 그리고 모델이 한 번의 추론에서 볼 수 있는 토큰 양에는 컨텍스트 윈도우(context window)라는 상한이 있어서 무한정 쌓을 수 없다는 것이다. 둘 다 2장에서 자세히 다룬다.

== 이 호출에서 책 전체로

지금까지의 해부에서 나온 질문들을 모으면 그대로 이 책의 목차가 된다.

[cols="2,3,1"]
|===
| 호출의 부분 | 생기는 질문 | 다루는 곳

| `model`
| 이 이름의 실체는 무엇이고, 모델은 어떻게 만들어지는가
| 1장, 2부

| `messages`
| 모델이 모르는 정보를 어떻게 공급하는가. 파인튜닝과 프롬프트 중 무엇을 쓰는가
| 1부, 4부

| `temperature`
| 무엇을 조절하며, 같은 입력에 왜 다른 출력이 나오는가
| 3장, 5장

| `usage`의 토큰 수
| 토큰은 어떻게 세어지고, 왜 입력과 출력의 단가가 다른가
| 6장, 9장

| `messages` 배열의 전달
| 이 배열은 어떤 형태로 모델에 도달하는가
| 9장

| 응답의 정확성
| 그럴듯한 답과 맞는 답의 간격을 어떻게 좁히는가
| 4부

| 모델 파일 자체
| 오픈 모델을 받으면 무엇이 들어 있고, 누가 만들었든 왜 바로 실행되는가
| 3부
|===

이 책은 이 표를 위에서부터 순서대로 채워 간다. 1부에서 파라미터와 messages라는 두 정보 경로의 지도를 그리는 것으로 시작한다.
